## Recovered scope and repository state

The interrupted task was to analyze `SPEC.md` and prepare a spec-driven implementation plan separated into waves. The nine wave documents had been written, but the final coverage, consistency and conformance reviews had not completed.

At recovery, the checkout was `main` at `18f07fd` (`first commit`). Only `README.md` and `SPEC.md` were tracked; `specs/` was untracked. There was no package manifest, source tree, test suite or CI configuration. The root specification remains unchanged. References to tests, ADRs, tools and deployment in the wave files describe future deliverables.

This review completes that planning task. It does not adopt SPEC 0.2.0, mark any wave done, or authorize provider spending, deployment, release publication or repository administration.

## Maintainer decisions and implementation entry

The proposal keeps U-1–U-5 defaults: mock tool executor, Responses streaming transport, SVG upload only in the playground, DCO sign-off and a single package with enforced boundaries. They remain proposed choices, not records of approval. The ORB-FORM-008 SHOULD-to-MUST clarification also needs explicit review in the amendment PR.

Once the plan is approved, the primary agent coordinates and reviews; coding, tests and targeted fixes go to the `coder` agent as required by the supplied AGENTS.md. The first implementation unit is W0 §4.1, using the current SPEC 0.1.0. W0 §4.5 then introduces requirement tooling against that baseline, and §4.8 adopts the reviewed 0.2.0 amendment before new-ID tests and the remaining foundation slices land. Each unit updates its evidence before another extensive unit begins.

W1/W2 may branch only after the shared type-only handoff. W4 similarly freezes the future audio/pointer/formation-source signatures before their implementation waves. Each gate still requires its own applicable tests, security mitigations and manual evidence.

Implementation-time verification remains explicit: pin and verify dependency versions, prove CSP/WebGL behavior in the production build, implement and negatively test import rules, verify workflow permissions and fork behavior, review the gateway hosting/state-store/auth boundary before any real-provider activation, and collect human/device evidence at the specified gates. W7's real-provider smoke requires a scoped budget authorization; W8 release/deployment requires publication authorization. These are future acceptance activities, not outstanding work needed to finish the planning document.
